# KeeperHub onboarding teardown — first run, Linux/WSL, 5 Aug 2026
Environment: Ubuntu on WSL2, x86_64, Node v24.13.0, no Homebrew, no sudo, headless (no browser on host)

1. Install docs are brew-first; no Linux path without reading GitHub Releases manually. **Doc fix: https://github.com/KeeperHub/cli/pull/88**
2. `kh --version` → "unknown flag". Correct form is `kh version`.
3. `kh auth login` documented as "opens a browser window"; actually a device-code flow. Codes expired repeatedly before I could use them on a remote/headless box. **Doc fix: https://github.com/KeeperHub/cli/pull/88**
4. BUG: `kh wallet info` (and all `kh wallet` agentic subcommands) fail with "could not determine executable to run". Root cause: `@keeperhub/wallet` publishes three bins (`keeperhub-wallet`, `keeperhub-wallet-hook`, `keeperhub-wallet-mcp`) — none named `wallet`. `npx @keeperhub/wallet <subcmd>` cannot infer which to run and exits. Fix is `npx -p @keeperhub/wallet keeperhub-wallet <subcmd>`. **Fix: https://github.com/KeeperHub/cli/pull/89** (Note: #88 added a Node prerequisite note treating this as a missing dependency — that diagnosis was wrong; the dependency is documented, the binary inference is the bug.)
5. BUG: `kh w balance` → "json: cannot unmarshal number into Go struct field ChainBalance.balances.chainId of type string". API returns chainId as number, CLI v0.13.1 expects string. Reproducible on every invocation, with and without --json/--chain. **Fix: https://github.com/KeeperHub/cli/pull/87**
6. `/plugin marketplace add KeeperHub/claude-plugins` clones over SSH → "Permission denied (publickey)" without GitHub SSH keys. Blocks the documented Claude Code path entirely; the `/keeperhub:login` and `/keeperhub:status` slash commands never become available. **Doc fix: https://github.com/KeeperHub/claude-plugins/pull/5**
7. BUG (silent failure): `create_workflow` over MCP silently drops node configs when they are passed at the top level — the workflow saves without error, `execute_workflow` returns `{ status: "running" }` without error, but only the trigger node fires; all action nodes are skipped. Root cause: node config must be nested inside the `data` object (`node.data.config`, `node.data.actionType`), not at the node's top level. Nothing in the API response, the execution status, or the run log indicates the config was ignored. This is a silent-success failure: every observable signal says it worked until you check `executionTrace` and see only `["trigger-1"]`.
8. `kh run logs <id>` returns 404 for direct executions (transfers, contract calls created via `kh execute` or `execute_transfer` MCP). There is no `kh execute logs` subcommand — `kh execute --help` lists only `status`, `transfer`, and `contract-call`. The workaround is `get_direct_execution_status` over MCP, but there is no documented CLI path to retrieve logs or receipts for a non-workflow execution.

9. BUG: Template substitution produces bare `NaN` when a node output field resolves to `undefined` (e.g. traversing a missing nested path like `result.currentATokenBalance` on a wallet with no Aave position). The substituted string `'NaN'` is passed to `JSON.parse()`, which throws `SyntaxError: Unexpected token N`. The workflow fails inside the code node with a runtime exception. Nothing in the error message identifies which substitution produced invalid JSON, or that the field was absent in the upstream output. Workaround: always guard template-substituted JSON strings: `JSON.parse('{{@node:Label.field}}' || '0')`. This is now in `guard-code` for all aDAI reads.

10. BUG (silent unit mismatch): `spark/vault-deposit.assets` requires a raw wei integer string (e.g. `"1912768697590422227"`), while `web3/approve-token.amount` requires a human-readable decimal string (e.g. `"1.912768697590422227"`). These two actions appear back-to-back in the approve → deposit sequence; their unit conventions are opposite and undocumented. `web3/check-token-balance` returns both: `balance.balance` (human) and `balance.balanceRaw` (wei). Wiring `balance.balance` into `spark/vault-deposit.assets` causes the deposit to call `deposit(1, receiver)` (1 wei, not 1 DAI), while the approve correctly approves 1.91 DAI — the approve tx succeeds, the deposit tx succeeds, but effectively zero capital moves. No error is raised. Fix: use `balance.balance` for `web3/approve-token.amount` and `balance.balanceRaw` for `spark/vault-deposit.assets`.

11. BUG (undocumented executing wallet): KeeperHub executes all onchain writes (`approve`, `deposit`, `supply`, `redeem`) with `msg.sender = Turnkey wallet` (`0x972A2E27b32152064F65a3Dda489F3899A168a37`), not the connected user wallet (`0xe1dC20C4Ed70b281441FA9b8324168DF4bdC11be`). This distinction is not surfaced in the workflow editor, API documentation, or any action schema. Consequences: (a) assets must be held at the Turnkey wallet address; (b) all `receiver`, `owner`, `account`, and `onBehalfOf` parameters must reference the Turnkey wallet; (c) approvals must originate from the Turnkey wallet. The only way to discover this is to see the transaction appear on Etherscan from the Turnkey address, not the user address. Approximately two days of debugging were spent on `deposit(0, receiver)` calls — the DAI was at the user wallet, not the Turnkey wallet. Fix: document the Turnkey wallet address prominently in onboarding; expose it in `kh wallet info` output and in the workflow editor's wallet selector.

12. BUG: `webhook/send-webhook` cannot call back into `api.keeperhub.com` from within a running workflow. KeeperHub's workflow execution environment fails to resolve its own API hostname, returning `"Cannot resolve host: api.keeperhub.com"` (error code `C-0001`). This means the documented pattern of chaining workflows via webhook (WF-3 guard → WF-2 rotate) is broken when the target workflow is on the same KeeperHub account. The design is correct; the platform DNS is the blocker. Fix: (a) add `api.keeperhub.com` to the allowed outbound hosts in the workflow execution sandbox; or (b) provide a native `workflow/invoke` action that triggers another workflow by ID without an HTTP round-trip.
